ClaimVerdict
Nothing shows as running True. No note carried running. Status is a self-report, and the dispatcher is the worker — an agent deep in a turn never stops to write it.
The panel doesn't reflect what's going on True, and structural. The panel had no independent signal at all. A 41-minute-old claim rendered identically to a live one.
New features weren't added to the graph False — VT-028…VT-035 were created at 17:31 and all 35 notes were correctly area-tagged. But nothing marked them as new, so in a 35-node graph they were invisible. The belief was wrong; the underlying gap was real.

Root cause in one line: the board rendered claims, never observations. The only thing a file-first panel can observe independently is when each note last changed on disk — the one timestamp a busy agent cannot forge. That is now what it shows.

Tracks: your own workflow, made addressable

You wrote that you might just run one pinned agent per track yourself. That is right, and it isn't a rival to this panel — the two halves are complementary. Pinned sessions give liveness you can see: a spinner, a crash, a usage limit, someone to talk to. The notes give durability those sessions don't have: they survive compaction, a closed tab, and the end of the session. So a track is now addressable from the command line.

How to work this lane
---------------------
1. Take one `ready` feature whose prerequisites are `done`.
2. Claim it — `vibetracks status <id> running` — BEFORE you start. The panel ages
   every claim; a `running` note unchanged for 15 minutes is shown as stale,
   so an unclaimed hour of work looks exactly like an idle hour to Zach.
3. Do the work. Touch the note as you go (`vibetracks comment <id> "..."`) — that is
   the heartbeat the panel can actually see.
4. Finish into `review` with a self-contained, media-rich HTML packet in `reports/`
   and link it from the note. Never set `done`; approving is Zach's gesture.
5. Blocked? `vibetracks status <id> waiting` and say what you are waiting on, in the note.
   An open question is `frontier`.

Stay inside this lane. Work in another area belongs to that track's agent:
file it with `vibetracks new "<title>" --area <other-area>` and move on.

The browser suite is repeatable — it builds its own track (one claim 47 minutes stale, one 2 minutes fresh), serves it on an ephemeral port, drives it, and tears it down. It found two real defects while being written:

  • #kanban with no area segment silently inherited whatever area filter was already selected, so a pasted link did not describe the board it opened.
  • touched was truncated to whole seconds, so a note changed in the same second you marked the board seen was never flagged as new — precisely the change most worth flagging. It now carries milliseconds.

Honest limit

mtime is a proxy. This can prove that nobody is reporting; it cannot prove that somebody is working. An agent that never claims its lane is still invisible — the panel now just says so out loud instead of looking empty and calm. Closing that gap properly needs a real heartbeat from the agent side, which AGENT.md now demands as a rule ("work you do not claim does not exist") rather than a suggestion.

Questions for you

1. Is 15 minutes the right patience before a running claim reads as stale? It is one constant, shared between app.js and tracks.py.

2. Do you want vibetracks track <area> to go further — actually launching a pinned per-track session — or is printing the brief for you to paste the right boundary? Printing keeps the tool out of your process management, which is where you said you can see crashes and usage limits.

3. The panel still cannot create features from the UI. When you paste context, that stays an agent gesture. Leave it that way?
